# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

**Bruno_Personal_Mcp** — a personal MCP server for Claude Desktop that will grow to cover multiple personal integrations (calendar, contacts, email, etc.). Modules:

- [bruno_calendar_mcp.py](bruno_calendar_mcp.py) — exposes the Apple Calendar (macOS) via EventKit: listing calendars/events, creating, deleting, and rescheduling events.
- [bruno_contact_mcp.py](bruno_contact_mcp.py) — exposes Contacts.app (macOS) via the Contacts framework: listing/searching contacts, finding likely duplicates, creating, updating, and deleting contacts.
- [bruno_mail_mcp.py](bruno_mail_mcp.py) — exposes Mail.app (macOS) via ScriptingBridge: listing accounts/mailboxes/messages, creating/deleting mailboxes, sending/replying/forwarding, moving, marking and deleting messages, downloading attachments.
- [bruno_notes_mcp.py](bruno_notes_mcp.py) — exposes Notes.app (macOS) via ScriptingBridge: listing accounts/folders/notes, creating/renaming/deleting folders, creating/updating/moving/deleting notes, downloading attachments.

See [MCP_MAIL_NOTES.md](MCP_MAIL_NOTES.md) for the design notes behind the Mail/Notes modules (data model, what's/isn't scriptable, known platform limitations).

## How to run

```bash
python3 bruno_calendar_mcp.py
python3 bruno_contact_mcp.py
python3 bruno_mail_mcp.py
python3 bruno_notes_mcp.py
```

The server communicates over stdio (that's how Claude Desktop connects), so running it directly in a terminal only verifies it starts without errors. Real testing happens through Claude Desktop, by registering the server in `claude_desktop_config.json`.

Live debugging (all logging goes to a file, never to stdout — stdout is the MCP protocol channel):

```bash
tail -f ~/bruno_mcp_debug.log
```

There are no tests, linter, or build configured.

## Dependencies

- `mcp` (MCP Python SDK, uses `FastMCP`)
- `pyobjc` (`EventKit`/`Foundation` frameworks for calendar, `Contacts` framework for contacts, `ScriptingBridge` for Mail/Notes)

macOS only. On first run the system shows a permission pop-up per data source (Settings > Privacy > Calendar / Contacts). Mail/Notes use a different permission category — see the Mail/Notes architecture note below.

## Architecture

- `FastMCP("bruno-calendar")` handles the whole protocol; each tool is a function decorated with `@mcp.tool()` that takes/returns plain strings.
- Existing tools: `list_calendars()`, `create_calendar(name, color, account)` (color belongs to the calendar in Apple Calendar — events inherit it; there is no per-event color in EventKit), `list_events(days_ahead, page, page_size)` (paginated, default `page_size=100`/max 500, to stay under the MCP response size limit; the footer tells Claude the next `page` to call when more results remain), `create_event(..., all_day, location, timezone, url)` (supports recurrence via `repeat`/`repeat_interval`/`repeat_until`; recurring saves need `EKSpanFutureEvents`; supports reminders via `alerts`, a comma-separated list of minutes-before-event, e.g. `'10,60'`, built into `EKAlarm`s via `_parse_alerts()`; `all_day` sets the real `EKEvent.allDay` flag and snaps start/end to midnight, with an exclusive end date per iCal convention; `location` is a plain string; `timezone` takes an IANA name, empty for the device's local zone, or `'floating'`/`'none'` for a wall-clock-fixed event — see the Floating gotcha below; `url` sets `EKCalendarItem.url` via `NSURL.URLWithString_`), `delete_event(event_id, scope, from_date)`, `reschedule_event(event_id, new_start, new_end, alerts, all_day, location, timezone, url)` (also the tool for changing alerts/all_day/location/timezone/url on an existing event — for each of these, empty leaves it unchanged, `'none'` clears it (or, for `all_day`, `'false'`), anything else replaces it). Write tools target events by the id shown in `list_events` output.
- **Floating time zone**: EventKit has no explicit "floating" enum — setting `EKEvent.timeZone` to `nil` is what makes an event keep the same wall-clock time regardless of time zone, matching Calendar.app's "Floating" option. `_parse_timezone()` maps `''` to the `_TIMEZONE_UNCHANGED` sentinel (only relevant on `reschedule_event`, where it means "don't touch the time zone") and `'floating'`/`'none'` to `None` (which callers pass straight to `setTimeZone_`). **Travel Time, Invitees, and Attachments are not exposed by EventKit's public API at all** — there is no way to add them from this server; they only exist in Calendar.app's own UI layer. `url` IS exposed (`EKCalendarItem.url`, inherited by `EKEvent`), unlike those three.
- **Deleting "from date X onward" must be ONE `delete_event` call** with `scope='this_and_future'` and `from_date=X` (the server re-anchors to the first occurrence on/after that date via `calendarItemExternalIdentifier`). Repeated calls on multiple occurrences truncate the series progressively backwards and can destroy past events — this happened once; there is a guard refusing past-dated truncation without an explicit `from_date`.
- **Recurring-event gotcha**: `eventWithIdentifier_` returns the *first* occurrence of a series even when given an occurrence-specific id (`..._N` suffix). `_find_event()` handles this by falling back to a predicate search for the exact occurrence id — never call `eventWithIdentifier_` directly for occurrence-level operations. `delete_event` takes `scope` ('this' | 'this_and_future' | 'all', mapped to `EKSpanThisEvent`/`EKSpanFutureEvents`) and verifies the occurrence is actually gone before reporting success.
- `_ensure_access()` blocks on a `threading.Event` until macOS's async authorization callback responds (60s timeout). Every tool must call it before touching the `EKEventStore`. It uses `requestFullAccessToEventsWithCompletion_` (macOS 14+, required for writes) with a fallback to the older `requestAccessToEntityType_completion_`.
- Writes go through `saveEvent_span_error_` / `removeEvent_span_error_` with `EKSpanThisEvent`; in pyobjc these return a `(success, NSError)` tuple when `None` is passed for the error out-param.
- Date conversion: EventKit uses `NSDate`; convert with `NSDate.dateWithTimeIntervalSince1970_(dt.timestamp())` going in and `datetime.fromtimestamp(nsdate.timeIntervalSince1970())` coming back.
- Objective-C methods via pyobjc use underscores instead of colons (e.g. `predicateForEventsWithStartDate_endDate_calendars_`).

### bruno_contact_mcp.py

- `FastMCP("bruno-contact")`. Tools: `list_contacts(query, group, page, page_size)` (client-side substring filter over name/org/phone/email — `CNContactStore` has no simple full-text predicate — applied before paginating; paginated like `list_events`, same defaults/footer convention; each line also shows the contact's account via `_build_account_map()` and its groups via `_build_group_map()`; `group` optionally restricts the listing to one group's members), `find_duplicate_contacts()` (groups by exact case-insensitive full name or by phone number compared digits-only), `list_contact_accounts()` (lists `CNContainer`s — iCloud/Google/Exchange/On My Mac — with id, name, type), `list_contact_groups()` (lists `CNGroup`s — the "subfolders" inside an account, e.g. Family/Work — with id, name, owning account), `create_contact_group(name, account)` (creates a group under a given account; empty account = system default), `update_contact_group(group_id, name)` (renames a group), `delete_contact_group(group_id)` (deletes a group without touching its contacts), `create_contact(..., account, birthday, address, url, notes, groups)` (`account` is a container id from `list_contact_accounts`; empty = system default container; `groups` adds the new contact to group(s) at creation), `update_contact(contact_id, ..., add_to_groups, remove_from_groups)`, `delete_contact(contact_id)`. Write tools target contacts by the id shown in `list_contacts`/`find_duplicate_contacts` output.
- **Groups (`CNGroup`)**: a contact's group memberships are separate from its account/container — a contact belongs to exactly one container but can be in any number of groups. Like accounts, `CNContact` carries no group field directly, so `_build_group_map()` rebuilds identifier→group-names by asking each group which contacts it holds (`CNContact.predicateForContactsInGroupWithIdentifier_`), same cost-scales-with-groups-not-contacts pattern as `_build_account_map()`. `_resolve_group_ids()` accepts either a group id or its exact name (case-insensitive) in the `groups`/`add_to_groups`/`remove_from_groups`/`group` arguments, so callers usually don't need to call `list_contact_groups` first. Membership changes (`addMember_toGroup_`/`removeMember_fromGroup_`) go in the same `CNSaveRequest` as the contact create/update.
- `_build_account_map()`: `CNContact` carries no account field directly, so the id→account mapping is rebuilt per call by asking each `CNContainer` which contacts it holds (`CNContact.predicateForContactsInContainerWithIdentifier_`) — cost scales with number of accounts, not contacts.
- **Moving a contact between accounts** (`update_contact(..., account=...)`): the Contacts framework has no native "move" operation. `update_contact` detects the target differs from `_contact_container_id()` and instead recreates the contact in the target container (`_clone_contact_for_move()` + `addContact_toContainerWithIdentifier_`, which also copies phones/emails/addresses/urls/birthday/note onto the fresh unsaved contact) and deletes the original in the same `CNSaveRequest` — this changes the contact's id; the response returns the new one.
- `delete_contact` re-fetches the contact after `executeSaveRequest_error_` returns `ok=True` and reports failure if it's still there — `ok` only reflects the local save, and for contacts in synced accounts (Google/iCloud/Exchange via CardDAV) the server-side deletion can lag or get reverted by a subsequent sync.
- `phones`/`emails` args use a `'label:value, label:value'` mini-format (e.g. `'mobile:+55 11 99999-9999, home:1122223333'`); a bare value with no label defaults to `mobile` for phones / `home` for emails. Labels include `personal` as an alias for `home`. `update_contact` REPLACES the whole list for a field when passed, it does not append — pass the full desired list; passing `'none'` clears it.
- `address` (postal addresses) uses `'label:street|city|state|zip|country; label:...'` (subfields between `|` may be left blank); `url` uses the same `'label:value, label:value'` mini-format as phones/emails, default label `homepage`. Both are parsed by `_parse_address_list()`/`_parse_labeled_list()` and applied via `_apply_addresses()`/`_apply_urls()`.
- `birthday` accepts `'YYYY-MM-DD'` (with year) or `'MM-DD'` (no year), parsed/formatted by `_parse_birthday()`/`_format_birthday()` into/from `NSDateComponents` — unset fields come back from pyobjc as a huge sentinel int (`NSDateComponentUndefined`), which `_format_birthday()` guards against.
- `notes` (`CNContactNoteKey`) is the one field Apple gates behind the `com.apple.developer.contacts.notes` entitlement, which this server doesn't have — reading/writing it typically fails silently or raises. `_notes_supported` is a module-level flag, `None` until the first fetch/save either succeeds or fails; once it's `False`, `_keys()` stops requesting `CNContactNoteKey` (so the rest of the contact data keeps working) and note reads/writes are skipped with a warning in the tool's response text instead of erroring.
- `_ensure_access()` mirrors the calendar module's pattern (`threading.Event` blocking on the async `requestAccessForEntityType_completionHandler_` callback, 60s timeout) but for `CNContactStore`/`CNEntityTypeContacts`.
- Writes go through a single `CNSaveRequest` per call (`addContact_toContainerWithIdentifier_` / `updateContact_` / `deleteContact_`) executed via `store.executeSaveRequest_error_`. Contacts fetched via `_fetch_contact()` (wraps `unifiedContactWithIdentifier_keysToFetch_error_` with the notes fallback above) are immutable (`CNContact`); call `.mutableCopy()` before editing, since only `CNMutableContact` can be saved.
- `find_duplicate_contacts()` is a heuristic aid, not an automatic merge/delete — it only lists candidate groups; the user decides what to remove via `delete_contact`.

### bruno_mail_mcp.py / bruno_notes_mcp.py

- **Different architecture from Calendar/Contacts**: Mail.app and Notes.app have no public EventKit-like framework — the only supported way to automate them is Apple Events (AppleScript's object model), reached here via `ScriptingBridge` (`SBApplication.applicationWithBundleIdentifier_("com.apple.mail" / "com.apple.Notes")`). Properties/commands are called as Python methods via dynamic classes (`app.classForScriptingClass_("outgoing message").alloc().initWithProperties_({...})`, then `.addObject_()` on the owning element array to "make" it) — never by building AppleScript/JXA source strings, which would risk script injection from user-supplied subjects/bodies. Full details and the real `sdef` dumps this was built from: [MCP_MAIL_NOTES.md](MCP_MAIL_NOTES.md).
- **Permission is Automation, not a data-access API**: unlike EventKit/Contacts (which have `request*Access*` callbacks), Mail/Notes automation is gated by the Automation TCC category (Settings > Privacy & Security > Automation), granted per calling process. A denied request fails **silently** — properties come back empty/nil rather than raising — so `_ensure_access()` in both modules can only check indirectly (`len(app.accounts()) > 0`) rather than detect denial directly.
- **`content`/`body` gotcha**: Mail's `message.content()` is declared as `rich text` in its dictionary, so ScriptingBridge returns a reference to that object, not a string — reading it needs an extra `.get()` (`_message_text()` in `bruno_mail_mcp.py`). Notes' `note.body()`/`note.plaintext()` are plain `text`-typed properties and come back as real strings directly — no `.get()` needed. Mixing these up silently returns an `SBObject` repr instead of the text.
- **Mailboxes have no native id** (unlike Notes' `folder`, which does): `bruno_mail_mcp.py` identifies one as `"account::nested/path"`, built forward from the same `mailboxes()` element traversal used to look it up later. Do **not** reconstruct this path backward via `mailbox.container()` — some providers (confirmed with Gmail's IMAP) expose hidden intermediate nodes through `container()` (an invisible `"[Gmail]"` namespace) that never appear in the forward `mailboxes()` listing, so a backward walk produces a path `_find_mailbox()` can never match.
- **Message ids are mailbox-scoped**: Mail has no flat, app-wide message collection (unlike Notes, see below), so `bruno_mail_mcp.py` encodes a message id as `"mailbox_ref::numeric_id"` and `_find_message()` resolves it by first finding that one mailbox, then scanning only its `messages()` — this keeps lookups bounded instead of scanning every account.
- **Notes has flat, app-wide collections**: `app.accounts()`, `app.folders()` and `app.notes()` (via the `application` class-extension) return every object system-wide regardless of nesting, so `_find_folder()`/`_find_note()` in `bruno_notes_mcp.py` search that flat list directly instead of walking the account/folder tree. Smart Folders aren't scriptable and never appear in `folders()`.
- **`send_message`/`reply_message`/`forward_message`** all funnel through one helper, `_compose_and_send()`, which builds an `outgoing message`, best-effort attaches local files (skipped individually, not fatal, if a path doesn't exist or attaching fails), and calls `.send()`. Reply/forward compose a **new** message (subject prefixed `Re:`/`Fwd:`, original quoted in the body) rather than using Mail's native `reply`/`forward` commands, so they aren't linked to the original via `In-Reply-To` headers — this sidesteps uncertainty around those commands' exact ScriptingBridge argument binding. Sending requires an explicit `account=` whenever more than one account is configured, to avoid silently sending from the wrong address.
- Password-protected notes: `note.passwordProtected` guards `get_note`/`update_note` with a clear message instead of returning an empty body — there is no way to unlock a note via scripting.

## Important constraints

- **Never write to stdout/stderr outside the MCP protocol** (no `print`): it corrupts the stdio communication with Claude Desktop. Use the `log` logger, which writes to `~/bruno_mcp_debug.log`.
- New integrations (email, etc.) should follow the same pattern: `@mcp.tool()` functions, file-based logging, explicit permission handling.
